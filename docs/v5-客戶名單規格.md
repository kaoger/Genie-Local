# Genie-Local v5 規格：客戶名單＋回報聯絡結果＋登入

> 撰寫：Claude。討論：Codex（正方：可行性）、Grok（反方＋資料蒐集）。決策：使用者。
> v5 草稿：2026-09-29；**v5 定稿：2026-09-29**（納入兩方審查與使用者 4 項決定）。
> 實作：Codex。複查與驗收：Claude。資料庫 SQL 與部署由使用者操作、Claude 逐步指引。

## 0. 一句話

Genie-Local 新增「客戶名單」頁：登入後讀取 Messenger 機器人寫進 Supabase 的客戶，待聯絡的排最上面，可直接回報聯絡結果。手機和電腦都能用。**本機專案功能不變、不需登入。**

## 1. 決策紀錄

| 題目 | 決定（2026-09-29） |
|---|---|
| 在哪裡用 | 手機＋電腦 → 放上使用者的 VPS（Traefik＋nginx，新子網域） |
| 誰登入 | 使用者本人與家人（多帳號）→ 沿用既有 `app_admins` 成員表，加人在 Supabase 後台操作 |
| 第一版範圍 | 名單＋回報聯絡結果。**「建立專案」延到「專案存進資料庫」的階段**（避免客戶電話多一份存在各裝置、兩套資料打架） |
| 登入程式 | 使用 Supabase 官方 supabase-js，**固定版本、檔案放進 repo（同源供應，不從 CDN 載入）**；AGENTS.md 規則同步修訂 |
| 保持登入 | 保持登入（supabase-js 預設 localStorage），頁面提供登出；手機遺失時由管理者在後台停用帳號 |
| 信件按鈕 | 保留；名單頁與信件寫同一組欄位 |

## 2. 情境（驗收）

1. 手機打開網址 → 左側選單點「客戶名單」→ 出現登入畫面 → 輸入帳號密碼。
2. 名單「待聯絡」區最上面是最早送出、尚未聯絡的客戶：服務／地區／坪數／預算／開始時間／聯絡時段／姓名／電話（點擊撥號）／送出時間（相對）。超過 3 天未聯絡標紅。
3. 打完電話按「約丈量」→ 該筆移到「已聯絡」區，顯示「約丈量・剛剛」。資料庫的聯絡時間由資料庫自己寫入。
4. 電腦重新整理 → 同樣看到「約丈量」。從信件按鈕記錄的結果，名單頁也看得到。
5. 未登入：本機專案照常可用；客戶名單只顯示登入畫面。直接用 publishable key 呼叫 API → 讀不到任何客戶（權限錯誤，不是空陣列）。
6. 登入的帳號不在 `staff` 或已停用 → 「此帳號沒有權限，請聯絡管理者」，讀不到資料。

## 3. 範圍

**要做**：資料庫權限、登入／登出、客戶名單（待聯絡／已聯絡）、回報聯絡結果、部署到 VPS。
**不做**：建立專案、專案存資料庫、成員管理畫面、改或刪客戶資料、AI、LINE、遮蔽電話。
**不能動**：Messenger 機器人、客人看得到的表單、本機專案的既有行為。

## 4. 架構

```
瀏覽器（手機／電腦）
 └─ Genie-Local 靜態檔（VPS：nginx 容器，經 Traefik HTTPS）
     ├─ 本機專案：localStorage（不變、不需登入）
     └─ 客戶名單：vendor/supabase.js（固定版本）
          ├─ Supabase Auth：密碼登入、自動續期、登出（scope=local）
          └─ PostgREST：apikey＝publishable key；登入後帶使用者 token
               └─ 權限：GRANT（哪些欄）＋ RLS（哪些列、誰）
```

- 前端只放 **publishable key**（`sb_publishable_…`，設計上公開）。放在 `config.js`，只放在 `apikey` 用途（由 supabase-js 處理），**不可當 Bearer**。secret key 絕不進前端。
- 兩個 repo 都是公開的：不得提交任何 secret、個人信箱、客戶資料。

## 5. 資料庫（Step A）

### 5.1 稽核（先做，不改任何東西）
使用者在 SQL Editor 跑唯讀查詢（Claude 提供），回報：`customer_leads` 是否已啟用 RLS、現有 policy 名稱、`anon`／`authenticated` 的表與欄位權限。現有 permissive policy 若會多放行，必須在 5.2 一併移除。

### 5.1 稽核結果（2026-09-29，使用者執行）
- 所有 public 資料表 RLS 皆已開啟。
- 已有 `app_admins`（`user_id`、`created_at`；1 人；policy：本人只能讀自己）與 `customer_leads` 的 admin select／insert／update policy（條件：`app_admins` 有本人）。
- **問題**：`customer_leads_anon_insert`、`lead_events_anon_insert`（anon、CHECK true）→ 任何持 publishable key 的人可灌假客戶；`authenticated` 對 `customer_leads` 有表層 INSERT／SELECT／UPDATE；`messenger_sessions` 對 anon／authenticated 有 REFERENCES／TRIGGER／TRUNCATE。
- 使用者（2026-09-29）：先由**使用者本人與家人**使用 → 多個帳號。

### 5.2 權限 SQL（Codex 撰寫 `ops/genie-access.sql`，放在 VPS-message repo；使用者執行）
**沿用 `app_admins` 當成員表，不另建 `staff`**（下文 staff 一律指 `app_admins` 中 `active = true` 的人）。
1. `app_admins` 加欄位：`display_name text`、`active boolean not null default true`。policy 不變（本人只能讀自己）；前端不可寫。
2. 移除 anon 寫入：drop `customer_leads_anon_insert`、`lead_events_anon_insert`；`revoke insert … from anon`。`messenger_sessions` revoke anon／authenticated 的 REFERENCES、TRIGGER、TRUNCATE。
3. `customer_leads`：
   - `revoke all … from public, anon, authenticated`。
   - `grant select (明列欄位)` 給 authenticated（id、status、answers、customer_name、phone、project_type、location、interior_area、budget_range、start_time、completed_at、contact_result、contact_result_at、contact_first_at、lead_grade、notification_status）；**不含** `outcome_token_hash` 等內部欄位。
   - `grant update (contact_result)` 給 authenticated（只有這一欄）。
   - drop `customer_leads_admin_insert`；重建 select／update policy，條件改為 `app_admins` 有本人**且 active**，update 同時寫 using 與 with check。
   - `BEFORE UPDATE` trigger：`contact_result` 改變時由資料庫設 `contact_result_at = now()`、`contact_first_at = coalesce(舊值, now())`；拒絕由非 null 改回 null。須相容 VPS `/lead/outcome`（service role）的寫法。
4. 其他 admin policy（flows、questions、question_options、flow_output_fields、lead_events 的 admin 讀寫）本版不動。
5. 整段包交易、可重跑，結尾 `notify pgrst, 'reload schema'`。

### 5.2a 執行紀錄（2026-09-29）
- 使用者已執行 `ops/lead-scoring.sql`、`ops/contact-result.sql`、`ops/genie-access.sql`（VPS-message `feat/contact-outcome` 分支版本）；`app_admins`：1 人、啟用 1。
- 公開註冊已關閉；已建測試帳號（非成員，Gmail `+test` 別名）。
- `ops/queries/genie-access-verify.sql`：**GENIE_ACCESS_OK**（anon／非成員／停用成員／成員／service_role 全部格子通過）。
- Claude 以 publishable key 實打 REST：anon 讀客戶、新增客戶、新增 lead_events、PATCH、讀 app_admins、讀 token hash → 全部 **42501**。
- 待補：機器人真實表單送出一次（確認 service_role 寫入與通知信正常）。

### 5.3 後台設定（使用者操作）
- Authentication：**關閉公開註冊**（Allow new users to sign up = OFF）。
- 新增使用者（本人、家人），再於 `app_admins` 插入一列並填 `display_name`（SQL 由 Claude 提供）。確認現有那 1 位 admin 是誰。

### 5.4 驗收（真實資料庫，不可只靠模擬）
用 publishable key 與真實帳號，逐項打 API：
| 身分 | 讀客戶 | 改 contact_result | 改 phone |
|---|---|---|---|
| 未登入 | 權限錯誤 | 權限錯誤 | 權限錯誤 |
| 已登入、非 staff | 0 列 | 0 列 | 權限錯誤 |
| staff | 可讀、看不到 token hash | 成功、時間由資料庫填 | 權限錯誤（42501） |
另驗：寫入聯絡結果後 **不會重寄通知信**；機器人新增與修改客戶、信件確認頁仍正常。

## 6. 前端（Step B～D）

### 6.1 檔案
- 新增 `vendor/supabase.js`（固定版本，README 記版本與來源 URL、SHA-256）、`config.js`（Supabase URL＋publishable key）、`auth.js`（登入狀態）、`leads.js`（名單與回報）。以 `<script defer>` 載入，單一命名空間；`app.js` 只加路由與選單（約 50～100 行）。
- 路由：新增 `#/leads`，未登入顯示登入畫面；其餘路由與本機專案行為不變。
- 所有輸出經 `esc()`；查詢一律明列 `select` 欄位，不用 `*`。

### 6.2 登入（Step B）
- 信箱＋密碼。錯誤一律「帳號或密碼錯誤」。登入後查自己的 `staff` 列：沒有或未啟用 →「此帳號沒有權限，請聯絡管理者」並登出。
- 保持登入；右上角顯示登入者名稱與「登出」（`scope: 'local'`，只登出這台）。
- 忘記密碼：顯示「請聯絡管理者重設」（免費方案內建寄信每小時僅 2 封，不做自助重設）。

### 6.3 客戶名單（Step C）
- 只查 `status = 'complete'`。
- **待聯絡**（`contact_result is null`）：`completed_at` 舊到新，一次 50 筆，「載入更多」。
- **已聯絡**：`contact_result_at` 新到舊，一次 20 筆，「載入更多」。
- 顯示欄位同情境 2；`lead_grade` 有值才顯示等級；`notification_status = 'failed'` 顯示「通知信寄送失敗」。
- 「重新整理」按鈕；頁面回到前景（`visibilitychange`）時自動重讀。
- 手機優先排版（卡片），電腦可用表格；空清單顯示「目前沒有待聯絡的客戶」。

### 6.4 回報聯絡結果（Step D）
- 四個按鈕：已聯絡／約丈量／沒興趣／聯絡不上。按下直接寫入（只送 `contact_result`），成功後移到已聯絡區；可再改。
- 失敗顯示錯誤並保留原狀；401 由 supabase-js 續期後重試一次，仍失敗 → 回登入畫面。

## 7. 部署（Step F）

- VPS 新增 `genie-web` 容器（nginx:alpine，唯讀掛載靜態檔），Traefik 規則 `Host(app.sameheart-design.com)`，沿用 Let's Encrypt。
- 安全標頭：CSP（`default-src 'self'`；`connect-src 'self' https://<project>.supabase.co`；`frame-ancestors 'none'`）、`Referrer-Policy: no-referrer`、`X-Content-Type-Options: nosniff`、`Cache-Control`（HTML 不快取）。
- 使用者：新增 DNS 記錄；在 VPS 執行部署指令（Claude 帶步驟）。
- Traefik access log 檢查（與 VPS-message 上線前檢查相同）。

## 9. 已知風險與後續

1. **Supabase 免費方案 7 天低活動會暫停**：暫停期間機器人存不了客戶、名單讀不到。需另外決定（升級 Pro 或其他做法）。
2. 客戶電話會出現在已登入的手機與電腦瀏覽器；防線是登入＋權限＋CSP＋手機遺失時停用帳號。
3. `staff.role` 目前不影響權限（所有啟用成員權限相同），加人前再決定是否區分。
4. 「建立專案」與「專案存資料庫」為下一版。

## 10. 兩方審查採納紀錄

- **Codex 採納**：supabase-js 固定版本、拆檔、`#/leads` 路由、明列 select、伺服器端排序分頁、SQL 草稿、trigger 保護時間欄、先稽核再改權限、欄位對照（留待建立專案版）、工時估算。
- **Grok 採納**：publishable key 只放 apikey、欄位 GRANT 需先 revoke 表層權限、`revoke anon`、關公開註冊、真實資料庫驗收矩陣、登入只擋名單頁（本機專案可離線）、不用 GitHub Pages、免費方案限制（寄信 2 封／小時、7 天暫停）、第一版縮小範圍。
- **未採納**：遮蔽電話（本工具用途就是撥號）；sessionStorage（使用者選擇保持登入）；VPS 唯讀 API 取代直連（改以 GRANT＋RLS＋真實驗收控管）。
