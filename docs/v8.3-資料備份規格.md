# v8.3 資料備份與還原演練 — 規格（定稿）

## 0. 背景與目標
- Supabase 專案 `sanhe-crm`（免費方案）沒有自動備份；v8 起客戶名單與專案的完整版只在雲端。
- 使用者 2026-10-06 決定：每日自動備份、異地＝使用者電腦每週自動拉、第一版不加密、失敗用 Healthchecks.io 寄信、還原演練在另開的免費 Supabase 專案。
- 範圍外：升級 Pro、即時複寫、PITR、Genie 前端顯示備份狀態、加密（後續版本）。

## 1. 備份範圍
- **整個 `public` schema**（結構、資料、RLS、GRANT、函式、trigger）：`pg_dump -Fc --schema=public --strict-names --quote-all-identifiers`，**不加 `--no-acl`**；`--no-owner` 在還原時使用。
- 2026-10-06 使用者檢查：`public` 18 個函式本體皆無 bearer／JWT 字樣（不含密鑰）。Database Webhook trigger 參數可能含 webhook 標頭，備份檔仍視為敏感。
- **不備份 `auth` schema**（避免密碼雜湊與 token 進備份）。出事時在新專案重建家人帳號，再把 `app_admins.user_id` 改成新 UUID。另於每次備份產出**不含密碼的成員對照表**（`app_admins` 的 `user_id`、`display_name`、`active`＋對應 `auth.users.email`）放在同一備份資料夾，供重建時對照。2026-10-06 使用者檢查：`public` 有兩個外鍵指向 `auth.users`——`app_admins.user_id`（`app_admins_user_id_fkey`）與 `flows.published_by`（`flows_published_by_fkey`）。還原必須分段：`pg_restore --section=pre-data` → `--section=data` → **在加回外鍵前**依成員對照表把 `app_admins.user_id` 改成新帳號 UUID、`flows.published_by` 改成新 UUID（或可為 NULL 時設 NULL）→ `--section=post-data`（加回外鍵、索引、trigger）。若 Supabase Admin API 允許以原 UUID 建立帳號，可作為替代路徑（實作前查證，不可假設）。成員對照表另含 `flows.published_by` 出現過的 user_id。
- 不備份 Supabase 託管物件（`extensions`、`net`、`realtime`、`supabase_functions` 等）；以文件記錄重建方式（見 §5）。

## 2. 每日備份（VPS）
- **主機 cron**（`CRON_TZ=Asia/Taipei`，每天 03:00）執行 `deploy/backup/backup.sh`，以 `docker run --rm` 跑官方 `postgres:<主版本>-alpine` 的 `pg_dump`，**不常駐容器、不加入 `hermes-agent-llsk_default` 網路、不發布埠、不掛 Docker socket**。映像主版本須 ≥ 伺服器版本（README 第一步查 `show server_version;`，以變數設定）。
- 連線：Supabase **session pooler，埠 5432**，使用者 `postgres.<project-ref>`，`sslmode=require`；不可用 6543 transaction pooler。
- 秘密：密碼放 `/etc/genie-backup/pgpass`（`PGPASSFILE`，0600），非秘密設定放 `/etc/genie-backup/backup.env`（0600）；Healthchecks ping 網址放同檔。**不放在 repo、不放命令列、不在 log 印出**；`docker compose config` 類指令一律 `-q`。
- 輸出：`/var/lib/genie-backup/`（0700；檔案 0600；`umask 077`），**在 `/docker/hermes-agent-llsk/data` 與 repo 之外**。
- 流程：檢查磁碟可用空間（低於門檻即失敗）→ `pg_dump` 直接寫暫存檔 → 結束碼 0 且 `pg_restore -l` 可讀且 `customer_leads` 有資料列（正式庫非空時）才原子改名 → 寫 manifest（時間、工具與伺服器版本、檔案大小、SHA-256、各表筆數；不含客戶內容）→ 保留 14 天（只清固定目錄與檔名格式，永遠保留最後一份成功備份）→ 全部成功才 ping Healthchecks。
- 不用管線串接（POSIX sh 無 pipefail）；每一步檢查結束碼。防重疊執行（lock）、設定逾時。

## 3. 異地：使用者電腦每週自動拉
- Windows 內建 OpenSSH `scp`＋工作排程器，每週一次把最新一份備份與 manifest 拉到使用者指定資料夾（例如 `D:\Backups\sanhe-crm\`），保留最近 8 份；以 manifest 的 SHA-256 驗證。
- 交付 PowerShell 腳本與設定步驟（SSH 金鑰登入、限制該金鑰只能讀備份目錄的方式由 README 說明）。電腦需開機才會拉；README 提醒啟用 Windows 磁碟加密（BitLocker／裝置加密）。

## 4. 失敗通知：Healthchecks.io
- 使用者自行註冊（免費），建立一個 check：週期 1 天、寬限 2 小時（約 26 小時沒 ping 就寄信）。ping 網址只放 VPS 設定檔。
- 只在整個流程成功後 ping；可選失敗時呼叫 `/fail`。ping 內容不含連線字串、路徑或資料。

## 5. 還原演練（一次性，另開免費 Supabase 專案）
- 使用者在 Supabase 後台新增測試專案（例如 `sanhe-crm-restore-test`），其連線資訊放 VPS `/etc/genie-backup/restore.env`／`restore-pgpass`。
- `deploy/backup/restore-drill.sh`：**目標 project ref 等於正式 ref（`llqwzrgzekalwdnetvyb`）或主機不在事先登記的測試 ref 時立即退出**；不使用 `--clean` 對正式庫。
- 步驟：在測試專案先建所需 extension 與 Database Webhooks（**保持停用**，避免寄信）→ 在測試專案建立測試成員帳號 → 依 §1 分段 `pg_restore --no-owner`（pre-data → data → 改對應 UUID → post-data；控制 trigger，避免改寫 version 或觸發通知）→ 執行驗證 SQL：各表筆數與 manifest 一致、RLS 啟用、四支 RPC（`genie_save_project`、`genie_delete_project`、`genie_restore_project`、`genie_undo_contact_result`）存在且權限正確、外鍵與 sequence 正常 → 輸出 `BACKUP_RESTORE_OK`。
- 使用者用測試成員登入測試專案的 REST（或臨時指向測試專案的本機 Genie）讀到名單與專案，才算演練完成。演練後可刪除測試專案。
- 另交付「真的出事時還原到新專案」文件：建專案 → 建帳號 → 還原 `public` → 改 `app_admins.user_id` → 重建 Database Webhook（新 URL、新 secret）與 Edge Function secrets → 更新 `config.js` 的 Supabase 網址與 publishable key、機器人環境變數 → 驗證。記錄已部署 Edge Function 清單與必要 secret 名稱（不含值）。

## 7. 驗收
- 本機：腳本 `sh -n`／`shellcheck`（若有）語法通過；以假 `pg_dump`／`pg_restore`（測試替身）驗證：失敗不改名、不刪舊檔、不 ping；空 `customer_leads` 判失敗；保留天數清理只動符合格式的檔；restore 腳本拒絕正式 ref。
- VPS（使用者照 README）：手動跑一次 → 產生 dump＋manifest、log 無秘密 → Healthchecks 收到 ping → 隔天 03:00 自動跑。
- 還原演練：`BACKUP_RESTORE_OK`＋測試成員能讀到名單與專案。
- Windows：手動執行一次拉取成功並通過 SHA-256。
- repo 與聊天紀錄無任何密碼、連線字串、ping 網址。
