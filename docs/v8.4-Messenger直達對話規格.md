# v8.4 名單「💬 Messenger」直達客人對話 — 規格（定稿，已含 Grok 反方修正）

## 0. 背景
- v5／v6.3：按「💬 Messenger」只能開收件匣＋複製姓名，因為 `selected_item_id` 實測無法指定對話，且 Conversations API 當時拿不到。
- 2026-10-25 Meta App Review 通過、10-27 App 發佈。Claude 於 10-27 用機器人的粉專權杖實測 `GET /me/conversations?platform=messenger&user_id={PSID}&fields=link`，回 `{"data":[{"link":"/157645098246646/inbox/<threadId>/?section=messages","id":"t_…"}]}`；使用者用平常的電腦瀏覽器點 `https://www.facebook.com` + link，**確認直接打開該客人的對話**。
- 使用者 10-27 決定「派工」。

## 1. 目標
名單卡片按「💬 Messenger」→ 直接開這位客人的 Messenger 對話。沒有對話編號的舊資料或查詢失敗時，維持現行「開收件匣＋複製姓名」，既有測試期望值不變。

## 2. 設計重點（Grok 反方後 Claude 裁決）
- **只存數字對話編號，不存整串網址**：`link` 是官方未文件化欄位，網址格式可能改。資料庫存 `messenger_thread_id`（純數字），網址由 Genie 前端用設定檔的 `metaPageId` 組成；格式改了只改前端一行。
- 寫入只碰這一欄；不走 `updateCustomerLead()`。（已查證：通知 webhook `notify-complete-lead` 只在 INSERT 觸發，UPDATE 不會重寄信；仍限定只改這一欄以免動到其他狀態欄。）
- 速率：官方 Conversations API 每個粉專每秒 2 次（[rate limiting](https://developers.facebook.com/docs/messenger-platform/overview/rate-limiting/)，來源支持）→ 回填間隔 ≥ 600ms。

## 3. 資料庫（三禾機器人 repo，Claude 經使用者同意後在正式庫執行）
- 新檔 `ops/genie-messenger-thread.sql`（不要改 `ops/genie-messenger-link.sql`）：
  - `customer_leads` 新增 `messenger_thread_id text`，可為 null；CHECK：null 或 `^[0-9]{1,30}$`。
  - `grant select (messenger_thread_id) on public.customer_leads to authenticated;`（讀取仍受既有啟用成員 RLS 限制）；anon 不給。機器人用 service_role，已有全表權限。
  - 最後 `notify pgrst, 'reload schema';`。
  - 可重跑（`add column if not exists`、約束先查 `pg_constraint` 再建）。
- 同步修改 `ops/genie-access.sql` 的 authenticated 欄位白名單，加入 `messenger_thread_id`（並確認 `messenger_user_id` 也在白名單內），避免日後重跑該檔把讀權拿掉。
- 驗收查詢 `ops/queries/genie-messenger-thread-verify.sql`：欄位與約束存在；`has_column_privilege('anon', …,'SELECT')` 為 false、authenticated SELECT 為 true、authenticated UPDATE 為 false；輸出 `THREAD_COLUMN_OK`。

## 4. 機器人（三禾機器人 repo）
- 新模組 `src/thread-link.js`：
  - `fetchThreadId(psid, { fetchImpl, token, pageId, graphVersion })`：呼叫 `https://graph.facebook.com/${GRAPH_VERSION}/me/conversations?platform=messenger&user_id=${psid}&fields=link`，Authorization header 帶既有粉專權杖（比照 `src/meta.js` 的取法，**不要** import `adminConfig()`），5 秒 timeout（AbortController）。
  - 回應形狀：取 `data[0].link`；`data` 空陣列 → 回 `{ status: "none" }`；有 `error` → 回 `{ status: "error", code }`（613／80006 視為 `rate_limited`）。
  - link 解析：容許前面帶 `https://www.facebook.com` 或 `https://business.facebook.com`、容許額外 query；用 `/^(?:https:\/\/(?:www|business)\.facebook\.com)?\/([0-9]+)\/inbox\/([0-9]+)\//` 取出兩段數字；第一段必須等於 `SANHE_PAGE_ID`，否則視為 none。成功回 `{ status: "ok", threadId }`。
- 掛鉤：在 `saveLead` 成功且實際寫進資料庫（storage 為 db）之後，**背景**執行 `attachThreadId(leadId, psid)`；聊天模式直接 `createCustomerLead` 的路徑也要掛。修改需求更新成功後也呼叫（函式內本來就只在原值為空時寫）。
  - 寫入：新函式（放 `src/supabase.js`）`setLeadThreadId(id, threadId)` → `update({ messenger_thread_id }).eq('id', id).is('messenger_thread_id', null)`。
  - 第一次結果為 none 時，5 秒後重試一次；仍失敗就放棄（回填可補）。
  - 一律 `.catch()`，只記固定事件名（`thread_link_none`／`thread_link_error`／`thread_link_rate_limited`），不記 PSID、編號、權杖。不得延遲表單回應、Messenger 摘要、通知流程。
- 回填 `scripts/backfill-thread-links.js`：查 `messenger_user_id` 非空且 `messenger_thread_id` 為空的名單，逐筆查詢，每筆間隔 ≥ 600ms；遇 rate_limited 立即停止並輸出「已處理到第幾筆」；可重複執行。輸出只有計數（成功／查無／錯誤＋錯誤碼統計），不印個資。由 Claude 在 VPS 容器內執行。
- 測試（假 fetch、假 store）：正常 link、帶完整網域、帶額外 query、粉專編號不符、空 data、error 613、timeout、寫入只在原值為空、背景失敗不影響表單送出、chat 路徑也觸發。既有 130 項全過，連跑 2 次。

## 5. Genie 工作台（Genie-Local repo）
- 欄位清單加 `messenger_thread_id`：`leads.js` 第 6 行的 SELECT、`tests/mock-leads.js` 的 SELECT、`tests/v7-leads.spec.js` 等引用處。
- `openMessenger(lead)`：
  - 若 `messenger_thread_id` 符合 `^[0-9]{1,30}$` 且 `messenger_user_id` 為數字 → 在**任何 await 之前**同步 `window.open(\`https://www.facebook.com/${encodeURIComponent(config.metaPageId)}/inbox/${threadId}/?section=messages\`, '_blank', 'noopener')`，不複製姓名、不跳提示。
  - 否則完全維持現行收件匣＋複製姓名＋提示（網址與文案不變）。
  - 網址不經 `esc()`（不放進 HTML），用格式白名單把關。
- Playwright：有編號時開對話網址；沒編號時沿用舊流程（既有測試不改期望）；編號含非數字（如 `1/../x`、`javascript:`）走舊流程。全套連跑 2 次全過。
