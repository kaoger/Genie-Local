# v9.0 流程待辦核心（分支自動化執行層）— 規格（定稿）

## 0. 目標與範圍
- 使用者 2026-10-07：事件發生後要有標準流程，例如約丈量之後一整套步驟，依結果走不同分支。本版只做**核心執行層**；各分支的實際步驟與天數之後由使用者定，本版用 §4 的**範例流程**（上線後可換版本）。
- 架構：核心放現有 Supabase（資料表＋資料庫函式＋觸發器）。n8n 不進核心，日後只做周邊（v9.3）。
- 原則：系統只做內部動作（建待辦、算到期、顯示下一步）；每一步結果由人選；不自動傳訊息給客人；不讓 AI 判斷；不改機器人程式。
- 討論紀錄：Codex 正方、Grok 反方（2026-10-07）。使用者決定：
  1. v9.0 做**中間版**：範本表＋自動接下一步＋在名單卡片上直接處理下一步。
  2. 負責人：**預設＝按聯絡結果的人**，下一步沿用上一步負責人；沒有人可指定（例如信件連結）時，v9.1 提醒寄給**所有啟用成員**。之後可能多位負責人。
  3. 不另開「今日待辦」頁；**下一步直接顯示並在卡片上處理**。
- 範圍外（v9.0）：跳過、改期、手動指派負責人、成員名單、提醒寄信、今日待辦頁、專案頁顯示、統計、n8n、拖拉式流程編輯器、替舊名單補建流程。

## 1. 名詞（白話）
- **流程範本（playbook）**：某個聯絡結果（例如「約丈量」）要接的一串步驟，以及每一步可選的結果各接到哪一步。
- **流程輪次（run）**：某位客人每次「聯絡結果真的改變」就開新的一輪。例：先按約丈量（第 1 輪）→ 收回 → 再按約丈量（第 2 輪）。舊輪次保留紀錄、不再續走。
- **待辦（task）**：某一輪裡的某一步，一筆一列。
- 一位客人同時最多一個**進行中**的輪次；一個輪次同時最多一筆**未完成**待辦（v9.0 只有單一路徑，沒有平行分支、沒有迴圈）。

## 2. 資料（新檔 `ops/genie-lead-tasks.sql`，可重跑；`public` schema，全部開 RLS）
| 表 | 主要欄位與限制 |
|---|---|
| `lead_playbooks` | PK `(playbook_key, version)`；`start_result`（四個聯絡結果之一）、`start_step_key`、`title`、`active bool`。同一 `start_result` 最多一個 active（部分唯一索引）。 |
| `lead_playbook_steps` | PK `(playbook_key, version, step_key)`；`label`、`due_kind`（`offset`＝建立後固定時數；`input`＝完成上一步時由人填日期時間）、`due_offset interval`（offset 才有，CHECK 對應）、`sort`。 |
| `lead_playbook_transitions` | PK `(playbook_key, version, step_key, outcome_key)`；`outcome_label`、`next_step_key`（null＝流程結束；非 null 須為同版本步驟，外鍵）、`sort`。 |
| `lead_playbook_runs` | `id uuid`、`lead_id → customer_leads.id`、`run_no`、`playbook_key/version`、`source_result`、`status`（`active`／`superseded`＝結果改了／`undone`＝收回／`finished`）、`started_at`、`ended_at`。`UNIQUE(lead_id, run_no)`；每位客人最多一筆 active（部分唯一索引）。 |
| `lead_tasks` | `id uuid`、`run_id`、`lead_id`（查詢用冗餘）、`step_key`、`status`（`open`／`done`／`cancelled`）、`due_at timestamptz not null`、`outcome`、`note`（≤500 字）、`previous_task_id`（unique）、`created_at`、`completed_at/by`、`cancelled_at`、`cancel_reason`、`version int`（樂觀鎖，>0）。`UNIQUE(run_id, step_key)`；每輪最多一筆 open（部分唯一索引）。狀態與欄位組合用 CHECK 鎖住（注意 NULL 會通過 CHECK，要寫明）。 |
| `lead_task_assignees` | PK `(task_id, member_id)`；`member_id → app_admins.user_id`、`assigned_at`。v9.0 只由系統寫入，畫面不顯示也不能改。 |
| `lead_task_errors` | `id`、`lead_id`、`contact_result`、`sqlstate`、`message`、`created_at`。觸發器出錯時寫這裡。 |

- 客人名單被刪除時：流程、待辦、負責人、錯誤紀錄一併刪除（`on delete cascade`）。理由：Meta 資料刪除要求必須能刪乾淨。
- 權限：
  - 啟用成員（`app_admins.active`）可讀以上所有表；anon、非成員、停用成員全拒。
  - 表層一律不給 anon／authenticated／service_role 寫入權限；寫入只走觸發器與 RPC。
  - 所有函式 `SECURITY DEFINER`、`set search_path = ''`、完整 schema 名稱；先 `revoke all ... from public, anon, authenticated, service_role` 再明確授權（v8.3 演練發現新專案預設會多給 anon 執行權）。觸發器函式不授權給任何角色。
- 範例流程（§4）由同一檔案的種子段落寫入；重跑不覆寫已存在的版本。

## 3. 規則
### 3.1 觸發器（聯絡結果改變時）
```sql
AFTER UPDATE OF contact_result ON public.customer_leads
FOR EACH ROW WHEN (OLD.contact_result IS DISTINCT FROM NEW.contact_result)
```
- 不碰既有 `genie_set_contact_timestamps`（BEFORE）；AFTER 看到的是它校正後的值。不加 INSERT 觸發器。
| 結果變化 | 同一交易內 |
|---|---|
| 空 → 有結果 | 有 active 範本：開新輪次（`run_no`＝該客人最大值＋1）＋建第一步。沒範本（沒興趣、聯絡不上）：什麼都不建。 |
| 結果 A → 結果 B | 舊 active 輪次標 `superseded`、其 open 待辦標 `cancelled`（原因 `result_changed`），再依 B 照上一列處理。 |
| 有結果 → 空（15 分鐘收回） | 舊輪次標 `undone`、open 待辦 `cancelled`（原因 `undone`），不建新的。 |
- 第一步到期＝`NEW.contact_result_at + due_offset`。
- 負責人：`auth.uid()` 是啟用成員就寫入 `lead_task_assignees`；不是（例如信件連結由機器人寫入）就不寫，視為「沒有負責人」。
- **出錯不能擋聯絡結果**：整段包在 `BEGIN … EXCEPTION WHEN others` 裡，失敗時這段的變更全部撤回、寫一筆 `lead_task_errors`，聯絡結果照常存檔。理由：四個結果按鈕、收回、信件連結（FB 審核期間）不能因為待辦出錯而壞掉。
- 觸發器不改 `customer_leads` 任何欄位、不改通知狀態、不發 HTTP。

### 3.2 RPC `genie_complete_task(p_id uuid, p_expected_version int, p_outcome text, p_note text default null, p_next_due_at timestamptz default null) returns jsonb`
- 回傳 `{status, version, next_task_id}`；`status` ∈ `completed`／`conflict`（版本不符）／`inactive`（輪次已不是 active、待辦不是 open、或名單結果已不等於輪次的 `source_result`）／`not_found`／`invalid`（結果不在範本內、下一步需要日期卻沒給、備註太長）。
- 先確認啟用成員，否則 `42501`。
- **鎖定順序固定：名單列 → 輪次 → 待辦**（先無鎖查出 `lead_id`，再依序 `FOR UPDATE` 並重新驗證）。不可反過來，避免和收回、改結果互卡。
- 下一步：
  - `offset`：到期＝完成時間＋`due_offset`，忽略 `p_next_due_at`。
  - `input`：`p_next_due_at` 必填，否則 `invalid`，整筆不動。
  - `next_step_key` 為 null：輪次標 `finished`。
- 本步標 `done`、填結果、備註、完成人與時間、`version+1`；建下一步並**複製本步的負責人**。全部同一交易。
- 授權：只 `grant execute ... to authenticated`。

### 3.3 時間
- 資料庫一律 `timestamptz`；畫面一律以 `Asia/Taipei` 顯示，不看裝置時區（沿用 `app.js` 既有台北日期轉換）。
- 「一天」＝24 小時，不算工作日。
- 日期時間輸入框（`datetime-local`）的值一律當台北時間（+08:00）送出。

## 4. 範例流程（version 1；之後由使用者換成正式版）
**約丈量（`site_visit`）**
| 步驟 | 到期 | 結果 → 下一步 |
|---|---|---|
| 確認丈量時間 | 按下後 24 小時 | 已約好時間 → 到場丈量；客人取消 → 結束 |
| 到場丈量 | 完成上一步時填日期時間 | 已丈量 → 整理資料並報價；沒丈量到 → 結束 |
| 整理資料並報價 | 完成後 72 小時 | 已報價 → 結束 |

**已聯絡（`contacted`）**
| 步驟 | 到期 | 結果 → 下一步 |
|---|---|---|
| 追蹤意願 | 72 小時 | 有興趣 → 再次追蹤；沒興趣 → 結束 |
| 再次追蹤 | 7 天 | 已追蹤 → 結束 |

沒興趣、聯絡不上：不建流程。

## 5. 畫面（只改 `leads.js`、`styles.css`）
- 範圍：「已回報」區的名單卡片。待聯絡卡片不變；專案頁不變。
- 讀取：該頁卡片的 open 待辦與該客人最新輪次**一次批次讀**（`in.(...)`），範本步驟與結果每次啟用名單頁讀一次快取；不要每張卡一個請求。沿用現有 epoch／請求失效機制（換帳號、離開頁面、晚到回應不覆蓋）。
- 卡片加一塊「下一步」：
  - 有 open 待辦：`下一步：確認丈量時間｜到期 10/9 14:00`，下面是該步的**結果按鈕**（文字來自範本）。
  - 到期狀態：已逾期＝🔴「已逾期 N 天」（未滿一天顯示小時）；台北今天到期＝🟡「今天到期」；其他不加顏色。文字＋顏色並用，不只靠顏色。
  - 按結果按鈕 → 在卡片內展開確認區：選填備註（≤500 字）；下一步是 `input` 時多一個必填日期時間；「確定」「取消」。不用瀏覽器 `confirm()`。
  - 送出中按鈕停用。成功：重新讀這張卡的待辦並提示「已完成：○○」。`conflict`／`inactive`：提示「這筆剛被更新，已重新整理」並重新讀取。`invalid`：在確認區顯示原因。離線：不送出、不排隊，提示需連線。
  - 輪次 `finished`：顯示「✓ 流程已完成」。
  - 該客人最新一筆 `lead_task_errors.created_at >= contact_result_at`：顯示「⚠️ 下一步沒有建立成功，請通知管理員」。
  - 沒有輪次（沒興趣、聯絡不上、v9 之前回報的舊名單）：不顯示這塊。
- 改聯絡結果、收回之後，沿用現有重新整理流程，下一步會一起更新。
- 範本名稱、結果文字、備註一律經 `esc()`。手機版沿用 v7.2／v7.3／v8.1 規則：按鈕可換行、無橫向捲動、觸控目標 ≥44px。

## 6. 驗收
### 6.1 SQL（新檔 `ops/queries/genie-lead-tasks-verify.sql`，比照 `genie-projects-verify.sql`）
- 整份包在交易裡、最後 `ROLLBACK`，全部通過才輸出 `LEAD_TASKS_OK`。測試用名單在交易內建立，不動正式資料。
- 權限：anon／非成員／停用成員讀不到、不能執行 RPC；成員不能直接寫任何新表、不能執行觸發器函式。
- 事件：同結果重寫不建；一般欄位更新（姓名、電話、通知狀態）不建；INSERT 不建；收回後再按約丈量 → 第 2 輪，不撞唯一鍵；A→B 取消 A 的 open 待辦；沒範本的結果不留 A 的待辦。
- 分支：兩條範例流程所有結果都走通；`input` 不給日期 → `invalid` 且資料不變；完成後負責人複製到下一步；信件路徑（無 `auth.uid()`）建出的待辦沒有負責人。
- 錯誤：故意讓觸發器出錯（例如在交易內暫時停用範本必要資料）→ 聯絡結果仍存、`lead_task_errors` 多一筆。
- 樂觀鎖：舊版本 → `conflict`；名單結果已改 → `inactive`。
- 併發（可用兩個連線手動測，寫在檔案註解）：同時完成同一筆只一個成功、只一筆下一步；完成與收回同時不互卡。
### 6.2 Playwright（`tests/v9-*.spec.js`，用現有 mock 機制）
- 下一步顯示、三種到期狀態（含台北跨午夜、裝置時區不是台北）、完成並出現下一步、`input` 日期必填、流程完成、錯誤提示、conflict 重新整理、離線、XSS、手機版 375×812、沒有輪次的卡片不顯示。
- 既有全套連跑 2 次全過；`node --check` 通過。
### 6.3 使用者實測
- 對一位測試名單按「約丈量」→ 卡片出現「下一步：確認丈量時間」→ 按「已約好時間」並填日期 → 下一步變成「到場丈量」。再按收回 → 下一步消失。
