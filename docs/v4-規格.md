# Genie-Local v4 規格：完整一致的專案流程

> 由 Claude 與 Codex 討論（兩輪）後、使用者定案。實作者：Codex。複查：Claude。
> 範圍：只改 `index.html`、`app.js`、`styles.css`、`README.md`。維持純前端、免建置、無外部套件。
> **不做**：資料庫／Messenger 串接、提案匯出（之後接 AI 再做）、視覺與 3D 的實際內容、JSON 匯入、完整版本歷史。
> 不要動 `.backups/`、`assets/`。v3 備份在 `.backups/before-v4-*.zip`。

## 0. 核心原則

1. **每一步都能打開查看。** 條件只限制「生成／確認／標記完成」這些動作；不再用整頁鎖定畫面蓋住內容（v3 `stepBody()` 的鎖定卡要移除）。
2. **只有 5 種步驟狀態**（CSS class 用英文）：

| 狀態 | class | 意思 |
|---|---|---|
| 缺資料 | `missing` | 主要動作缺少必要輸入或前置步驟 |
| 可開始 | `ready` | 條件足夠，尚未人工確認（有草稿也算這個） |
| 已完成 | `done` | 人工確認過，且目前的依據和確認當下相同 |
| 需更新 | `stale` | 有確認紀錄（或已有成果），之後依據改變 |
| 不適用 | `na` | 本版不支援此類型，或本案選擇不採用 |

3. **人工確認只有兩種按鈕**：需求總覽「確認需求」；其他步驟「標記完成」。生成出內容 ≠ 已完成。
4. **完成時保存依據快照**：`p.steps[stepId] = { at: ISO時間, basis: basisOf(p, stepId) }`。狀態計算時比對 `basis` 與目前的 `basisOf()`，不同就是「需更新」。比對用「鍵排序後的 JSON」避免鍵順序造成誤判。
5. **所有會寫入的操作都要「存成功才生效」**：新增 `commit(change)`：先 `structuredClone(projects)` 備份 → 執行變更 → `save()`；失敗就還原 `projects` 並回傳 false。呼叫端失敗時**不關閉表單／對話框**。

## 1. 欄位定義（`app.js` 頂部）

保留原本的欄位設定方式，新增：
- 區塊屬性 `req:true`：此區塊的欄位屬於「需求」。聯絡資訊區塊與備註區塊**不是**需求（改電話、備註不會讓任何步驟需更新）。
- 欄位屬性 `est:true`：業務估價會引用。
- `ai:true` 維持為「必填」，徽章文字從「AI 必填」改成「必填」，title：「確認需求與生成策略企劃需要這個欄位」。
- 數字欄位（坪數）必須 **> 0** 才算有填（v3 的 "0" 會被當成已填）。

依類型分三套需求區塊：

| 類型 | 區塊 |
|---|---|
| 居家裝潢設計 | 沿用 v3 的「房屋概況」「空間需求」。`est`：houseType、area、layout、renoType、budget |
| 商業空間設計、展覽空間設計（新） | 「場地概況」：縣市、地址、坪數（ai, est）、開幕／展期月份（month）。「空間需求」：空間用途 `usage`（text, ai, wide，placeholder「例如：咖啡廳、辦公室、品牌展位」）、風格（chips 多選, ai）、施作範圍 `renoType`（chips 單選, ai, est：全區裝修／局部改裝／只要設計／展場搭建）、預算（est，用居家預算選項）、其他需求 |
| 品牌、包裝、網站、其他設計 | 沿用 v3「專案資訊」（section id 改成 `project`），新增「交付項目」`deliverables`（text, est, wide，placeholder「例如：Logo、名片、包裝盒」）；預算加 est |

**不同類型共用同一個 key 但選項不同**（budget、renoType）：select 與 chips 渲染時，若目前值不在選項內，要把它當成額外選項顯示並選取，不可以默默清空。

`reqOf(type, brief)` → `{ type, 各需求欄位: 正規化值 }`（空值一律 `''`）。

## 2. 資料模型與舊資料轉換

```js
{
  id, name, contact, phone, email, type, date, due, notes,   // top 欄位
  done,                 // v3 舊欄位：保留不刪，但新流程完全不讀
  brief: {...},
  source: { kind: 'manual'|'meeting'|'client'|'unknown', submittedAt?, meetingText?, fileName? },
  steps: { brief?, strategy?, visual?, model3d?, estimate?, proposal? },   // 每個是 {at, basis}
  skip:  { visual?: true, model3d?: true },   // 本案不採用
  strategy: { at, snapshot:{type, brief} } | undefined,    // 目前版（v3 格式相容）
  strategyPrev: 同上 | undefined,                          // 上一版
  estimate: { rows:[{id,item,qty,unit,price,areaLink?:'on'|'off'}], tax:'excl'|'incl', scope, validUntil } | undefined
}
```

`normalizeProject(p)` 於載入時執行：補 brief／type、`steps={}`、`skip={}`；沒有 source 的舊資料設 `{kind:'unknown'}`（**不要**從 `done` 推算）；刪除 `strategyStale`。
新建立的專案 `source.kind='manual'`。種子資料：原本 done=true 的設 `client` 並給 submittedAt，其餘 `manual`（只影響全新瀏覽器）。
複製專案：保留欄位、brief、estimate；清掉 steps、strategy、strategyPrev；source 設 manual。
匯出 JSON 的 version 改成 3。

## 3. 六個步驟的規則

`basisOf(p, id)`：

| 步驟 | basis |
|---|---|
| brief | `{ req: reqOf(p.type,p.brief) }` |
| strategy | `{ req, gen: p.strategy?.at ?? null }` |
| visual / model3d | `{ req, strategy: p.steps.strategy?.at ?? null }` |
| estimate | `{ deps: {type, 各 est 欄位值}, est: 解析後的估價（連動坪數的列帶入實際坪數） }` |
| proposal | `{ parts: proposalParts(p).map(id => [id, p.steps[id]?.at ?? null]) }` |

`proposalParts(p)` = brief、strategy、（visual 若適用且未 skip）、（model3d 同）、estimate。

`stepStatus(p,id)` 判斷順序：
1. model3d 且類型為品牌／包裝／網站 → `na`，meta「本版不提供」，原因「『{type}』本版未提供 3D 建模。」
2. visual／model3d 且 `p.skip[id]` → `na`，meta「本案不採用」
3. 有 `p.steps[id]` → basis 相同 `done`「已完成」，否則 `stale`「需更新」
4. strategy 有內容但 `snapshot` 的需求 ≠ 目前需求 → `stale`「需重新生成」
5. 其餘看「可開始條件」：不滿足 `missing`，滿足 `ready`

| 步驟 | 可開始（否則 missing 的 meta） | ready 的 meta | 標記完成／確認的阻擋條件（按鈕 disabled 並顯示原因） |
|---|---|---|---|
| ① 需求總覽 | 必填都有效（`必填 x/y`） | 可以確認 | 還缺必填欄位（列出名稱） |
| ② 策略企劃 | 需求已完成（需先確認需求） | 可以生成／待標記完成 | 需求未完成；尚未生成；策略依舊需求產生（須重新生成） |
| ③ 視覺發想 | 策略已完成（需先完成策略） | 待標記完成 | 需求或策略未完成 |
| ④ 3D 建模 | 同上 | 待標記完成 | 同上 |
| ⑤ 業務估價 | 永遠可開始 | 可以開始／編輯中 | 需求未完成；至少一筆有效明細（項目、數量>0、單價>0）；有內容但不完整的列要指名；報價範圍必填；有效期限必填 |
| ⑥ 提案簡報 | 需求已完成（需先確認需求） | 可以預覽 | proposalParts 中還沒 done 的步驟（列出名稱） |

**生成策略**只在需求 `done` 時允許；重新生成時把目前版移到 `strategyPrev`。策略 stale 且是因為需求改了 → 狀態列給「重新生成」按鈕；若只是重新生成後還沒重新標記 → 給「檢查後重新標記完成」。

**「需更新」要說清楚原因**（`staleReason`）：比對舊 basis 與目前 basis，組出例如「需求修改了：坪數、預算」「策略企劃已重新生成」「報價明細在完成後有修改」「引用的內容已更新：業務估價」。需求類型改變就只寫「需求類型」。需求總覽 stale 時同時列出目前缺少的必填欄位。

「取消完成／取消確認」：刪掉 `p.steps[id]`。

## 4. 各頁面

每一頁最上方都有**狀態列**（`<div id="status-slot">`）：標題（例如「需要更新」）、原因、動作按鈕。class `status-bar is-{狀態}`。

- **① 需求總覽**：狀態列（缺資料時含進度條＋缺少欄位的 chip＋「一次補齊」；齊全時「確認需求」；stale 時「重新確認需求」）→「需求來源」卡 → 小提示 → 各區塊卡片（沿用 v3，點欄位開側邊表單）。
- **需求來源卡**：三個分段按鈕（手動建立／會議記錄整理／客戶填寫），`unknown` 顯示「未註明來源（舊資料），請選擇」。
  - 手動建立：一句說明。
  - 會議記錄：textarea 貼上文字＋「參考檔名」輸入框（註明「僅記錄檔名，不保存檔案」）＋「儲存記錄」＋「對照記錄填寫欄位」（開側邊表單）。**貼上文字不會自動確認或改任何需求欄位。**
  - 客戶填寫：未登錄時按「記錄客戶已送出」→ 顯示「已送出・手動登錄 {時間}」與「取消登錄」。附註「之後串接 Messenger 機器人後，客戶送出會自動記錄。」
- **側邊表單**：若來源是會議記錄且有文字，表單頂部顯示可收合的「會議記錄（對照填寫）」。
- **② 策略企劃**：狀態列 → 沒內容時的空狀態卡（需求已完成才有「生成策略企劃（示範）」，否則「前往需求總覽」）→ 目前版文件（沿用 v3）→ 有上一版時用 `<details>` 顯示「上一版（時間）」。**即使需求缺欄位，舊策略仍要看得到。**
- **③ 視覺發想／④ 3D 建模**：狀態列 → 說明卡：這一步要做什麼、「會帶入的資料」（視覺：必填欄位；3D：坪數、格局、屋況、空間用途中該類型有的）、註明「示範版尚未製作內容，請在其他工具完成後回來標記完成；之後串接 AI 會在這裡生成」。卡片右上「本案不採用／改為採用」（3D 本版不提供的類型不顯示此按鈕）。
- **⑤ 業務估價**：狀態列 → 報價明細表（項目、數量、單位、單價、小計、刪除）＋「新增一列」→ 條件（稅別：未稅（另加 5% 營業稅）／含稅；有效期限；報價範圍與說明）→ 合計（小計、營業稅、總計、客戶預算＝需求的預算文字，只顯示不比較）。
  - 預設列：居家／商業／展覽 → 室內設計費（`areaLink:'on'`，單位坪）、3D 圖與施工圖（1 式）、工程監造（1 式）；其他類型 → 設計提案（1 式）、修改與完稿（1 式）。未編輯前不寫入資料。
  - `areaLink:'on'` 的列數量自動等於需求坪數，下方標「沿用需求坪數」；使用者改了數量 → `off`，標「自訂計價坪數」＋「改回沿用」。不反向改需求。
  - 編輯方式：`input` 事件只即時更新小計／合計顯示；`change` 事件才 `commit` 儲存，**不要整頁重繪**（避免使用者點下一格時焦點消失），只更新狀態列、步驟列、合計。新增／刪除列、改回沿用才整頁重繪。
- **⑥ 提案簡報**：狀態列 → 預覽：1 專案概要（名稱、聯絡人、類型、非空的需求欄位）、2 策略企劃、3 視覺發想／4 3D（僅適用且採用時；只顯示狀態）、5 業務估價（明細與合計）。每段標題旁有狀態小標籤。最後一張說明卡：「正式匯出（PDF／簡報）會在串接 AI 後提供，目前可在這裡檢查提案內容是否完整。」

**步驟列**：徽章 done ✓、stale !、na –、其餘數字；na 的名稱加刪除線、灰色；missing 灰色；ready 黑框。

**標記完成後**的 toast 提供「前往下一步」（下一個非 done、非 na 的步驟）。

## 5. 側邊表單修正

- 切換需求類型時，**先把目前表單值存進草稿**（`drawerDraft`），再依新類型重建；切回來時未儲存的修改要還在。
- 儲存時比對所有 top 欄位＋ brief 所有 key（含其他類型草稿），算出變更數；比對儲存前後的步驟狀態，toast 寫「已儲存 N 個欄位。需要更新：策略企劃、業務估價」並附「前往」按鈕（到第一個變成 stale 的步驟）。
- 移除 v3 的 `strategyStale` 邏輯。
- 儲存失敗時表單保持開啟。

## 6. 清單頁

- 欄位：勾選｜名稱｜聯絡人｜洽詢日期｜需求類型｜電子信箱｜電話｜專案到期日｜**需求來源**｜**目前步驟**｜操作。
- 需求來源：手動建立／會議記錄／客戶已送出（client 且有 submittedAt）／等待客戶填寫（client 未送出）／未註明。
- 目前步驟：依序找第一個「不是 done、也不是 na」的步驟，顯示 `② 策略企劃・需更新` 小標籤（顏色依狀態），連到該步驟；全部完成顯示「提案已完成」。
- **移除**紅綠燈按鈕、單筆切換、「標記已完成」批次操作。選取列改成「刪除所選」＋「取消選取」，刪除沿用確認對話框（多筆文案「確定刪除所選的 N 個專案？」）與 10 秒復原；復原要能還原**整批**（修正 v3 連刪兩次只能救最後一筆）。
- 「範例」列同步新欄位（來源、步驟顯示「—」）。
- 快速新增對話框的「名稱」改成「專案名稱」。
- 900px 以下表格 `min-width` 加大到約 1100px。

## 7. 其他

- 使用說明（help）與 `README.md` 改寫成 v4 流程；README 保留「調整欄位」說明並加入 `req`、`est`。
- 樣式延續現有黑白灰＋綠（done）＋琥珀（stale）；`button.primary:disabled` 必須仍看得到（現有 `button:disabled` 會把背景變透明）。
- 手機（≤600px）狀態列改直向排列，估價表可左右捲動。
- 程式風格延續現有 `app.js`（IIFE、`$`、`esc`、區塊註解）。所有使用者輸入輸出都要 `esc()`。

## 8. 驗收清單（Claude 會逐項實測）

1. 舊 v3 資料載入不報錯；舊專案來源顯示「未註明」；`done` 不影響任何狀態。
2. 全新瀏覽器：清單 8 筆示範資料、來源與目前步驟正確。
3. 新增專案 → 進入需求總覽，狀態「缺資料 必填 0/4」，其他步驟都能點開。
4. 補齊必填 → 「可以確認」→ 確認需求 → ② 變「可以生成」→ 生成 → 標記完成 → ③④⑤ 依規則變化。
5. 改坪數 35→40：需求總覽、策略、視覺、3D、估價（連動列）、提案都依規則變「需更新」並寫出原因；舊策略仍可看；估價連動列自動變 40。
6. 改電話或備註：沒有任何步驟變需更新。
7. 品牌設計專案：3D 顯示「不適用・本版不提供」；目前步驟會跳過它。
8. 視覺設「本案不採用」→ 提案不需要它就能完成。
9. 側邊表單：居家改到品牌再改回居家，未儲存的修改還在；budget 舊值不在選項時不被清空。
10. 坪數填 0 不算已填。
11. 估價：輸入時合計即時更新；Tab 到下一格焦點不會跳掉；改連動列數量 → 自訂計價坪數 → 改回沿用。
12. 刪除 2 筆 → 復原兩筆都回來、位置正確。
13. 模擬 localStorage 寫入失敗（例如覆寫 `Storage.prototype.setItem` 丟錯）：表單不關閉、畫面不顯示已儲存、資料不變。
14. 主控台無錯誤；375px 手機寬度沒有整頁橫向捲動。

## 9. v4.1 修訂（Grok 紅隊審查＋Claude 驗收後，2026-09-27）

第一輪實作驗收：14 項中 13 項通過；第 5 項失敗。Grok 指出的狀態連動問題全部在瀏覽器重現。以下修訂**優先於**前面各節的衝突內容。

### 9.1 已完成必須「自己的依據沒變」且「前置步驟目前都已完成」（連鎖規則）

前置關係：

| 步驟 | 前置步驟（必須目前是 done） |
|---|---|
| brief | 無 |
| strategy | brief |
| visual、model3d | strategy |
| estimate | brief |
| proposal | `proposalParts(p)` 中的每一步 |

`stepStatus` 對有完成紀錄的步驟：自己的 basis 相同**而且**所有前置步驟目前都是 `done` → `done`；否則 → `stale`。
- 只有前置不是 done（自己依據沒變）時，meta 用「上游需更新」，原因寫「『{前置步驟名稱}』目前不是已完成」。
- 前置恢復為 done、而自己的依據沒變時，**自動回到 done**，不需要重新標記。

已驗證的錯誤（修正後要消失）：取消確認需求後策略／視覺／3D／估價仍顯示已完成；重新生成策略後視覺／3D 仍顯示已完成；改坪數後提案仍顯示已完成。

### 9.2 下游依據改記「內容」，不記「完成時間」

| 步驟 | 新 basis |
|---|---|
| brief | 不變：`{ req }` |
| strategy | 不變：`{ req, gen: p.strategy?.at ?? null }` |
| visual | `{ fields: 本步「會帶入的資料」欄位值, gen: p.strategy?.at ?? null }` |
| model3d | `{ fields: 坪數、格局、屋況、空間用途中本類型有的欄位值, gen: p.strategy?.at ?? null }` |
| estimate | 不變：`{ deps, est }` |
| proposal | `{ header: {name, contact, type}, parts: proposalParts(p).map(id => [id, p.steps[id]?.basis ?? null]) }` |

- visual 的「會帶入的資料」與 basis 用同一份欄位清單（目前是 `aiFields`），畫面與判斷一致。
- 原因：只「取消再確認」而內容沒變，不應讓提案變需更新（第一輪已重現這個誤判）；重新生成策略則一定要讓視覺／3D 變需更新。
- `staleReason` 依新 basis 改寫：visual／3D 寫「策略企劃已重新生成」或「會帶入的資料修改了：{欄位}」；proposal 寫「引用的內容已更新：{步驟名稱}」或「專案名稱／聯絡人／類型已修改」。

### 9.3 其他規則補充

1. **策略的「重新生成」**：需求不是 done 時，按鈕換成連到需求總覽的「前往需求總覽」，不要顯示停用的重新生成。
2. **含稅公式**（維持第一輪實作）：未稅 → 營業稅＝小計×5%，總計＝小計＋稅；含稅 → 總計＝明細合計，內含稅額＝總計−總計÷1.05，未稅小計＝總計−稅額。四捨五入到小數兩位。
3. **正規化**（維持第一輪實作）：空值一律 `''`；字串去頭尾空白；數字欄位轉成數字；多選依字母排序；物件鍵排序後比較。
4. **估價列**：「有內容」＝項目、數量、單位、單價任一有值；有內容但不完整就擋住標記完成。自訂計價坪數（`areaLink:'off'`）的列，需求坪數改變時**仍讓估價需更新**（提醒業務覆核），這是刻意的。
5. **複製專案**保留 `skip`。**取消登錄客戶送出**只清 `submittedAt`，來源仍是客戶填寫。新增專案預設類型是居家裝潢設計。
6. **示範資料與範例列不得使用真實姓名或參考網站的真實範例**：示範專案名改成 `示範居家設計`；範例列改成 `示範品牌 / Demo Brand`、`示範聯絡人`。
